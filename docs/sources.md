## 事故: 警報エンドポイントの凍結を66日間検知できなかった（2026-08-01発覚）

**発端は032（ちゅらねこ日和）の実装中に発見された対照実測。** 沖縄4区に加えて東京
（130000）も同じ2026-05-28T10:1x時点で固定されていることを確認し、**沖縄固有ではなく
エンドポイント自体の停止**と判断した。

- 旧URL `warning/data/warning/{code}.json` は気象庁が2026-05-29に警報コード体系を
  「令和8年体系」へ移行した後も**廃止されず200を返し続けていた**が、中身は移行前日
  （2026-05-28）で完全に固定。3日予報 `forecast/data/forecast/{code}.json` は
  同時期も正常に更新され続けており、警報系統だけが取り残されていた
- 原因は当時の設計の誤り。「警報は変化があったときしか更新されない＝更新がない状態は
  正常」という前提（M1実測に基づく）が、「更新されない」と「ソースが死んでいる」を
  区別できない設計になっていた。HTTPステータスとJSONパース可否だけを見る異常判定では、
  **200を返し続けながら中身だけ固まる**壊れ方を検知できない
- 031の収集は2026-07-27開始・M1実測時点で凍結はすでに発生していた
  （凍結開始2026-05-28に対し収集開始07-27）。つまり**031が収集した警報レコードは
  発生した瞬間から全件が凍結後のもの**であり、収集の欠陥ではなくソース自体が
  最初から死んでいた。2026-08-01に新URLへ切り替えるまでの間、
  本来07-27〜08-01に出ていたはずの実発表（新URL側で `reportDatetime` が
  この期間のものが多数確認できた）を取得できていなかった
- 新URL `warning/data/r8/{code}.json` は正常稼働中（2026-08-01実測でLast-Modifiedが
  当日）。切り替え後、新URLが保持していた直近の発表を配列でまとめて取得でき、
  一部は遡って回収できた（下記「データの汚染範囲」参照）。ただし新URLでも
  同じ壊れ方が将来起きうるため、**発表時刻が閾値（既定7日）を超えて更新されなければ
  ジョブを失敗させる鮮度チェックを `scripts/collect.mjs` に追加した**
  （`checkStale()`。台風は活動中のTCで24時間閾値も別途チェック）

### データの汚染範囲

`data/warning/2026/07.jsonl` の**全4件（＝当データセットの全レコード）**が、
旧URLからの取得分＝取得は正しく行われたがソース側が2026-05-28以前の内容のまま
凍結していたもの。`warning_code_system` フィールドが無いレコードがこれに該当する。
**鮮度判定に使わないこと。** 過去レコードは書き換えず、この事実は README・本ファイルに
記録するにとどめる（追記専用の原則）。

2026-08-01の切り替え後、新URLが保持していた直近の発表（2026-07-11〜08-01分、
沖縄4区で21件）を `warning_code_system: "r8"` 付きで回収した。ただし新URLの配列が
何日分を保持するかは気象庁が仕様として約束しておらず、**2026-05-29の移行から
07-11までの発表は取得手段がなく永久欠損**（新URLの保持期間外・旧URLは凍結済み）。

## 実測でわかっている注意点（2026-07-27 M1 実測、2026-08-01追記）

- **これらの JSON は公開されているが非公式**（気象庁が API として仕様を約束しているものではない）。
  仕様変更・廃止があり得る。だから取得失敗を必ず検知して落とす設計にしてある。
  ただし「200を返しながら中身が死ぬ」壊れ方は取得失敗としては検知できない
  （上記「事故」参照）ため、鮮度チェックを別途追加している。
- **警報 JSON は発表内容に変化があったときしか更新されない。**
  M1 実測時点で沖縄4区の `Last-Modified` は2ヶ月前のままだった（＝発表なしの状態が続いている
  ように見えたが、実際にはエンドポイント自体の凍結だった。上記「事故」参照）。
  異常判定は HTTP ステータスとパース可否に加え、**発表時刻の鮮度**でも行う。
- 全エンドポイントに `ETag` と `Cache-Control: max-age=60` がある。警報は条件付き GET
  （`If-None-Match`）で 304 を受けられるので、平時の転送量はほぼゼロ。
- 警報コードの公式な対応表は JSON では配信されていない
  （`common/const/warningcode.json` は 404）。コードは生のまま保存し、
  対応表は [README.md](../README.md) に手書きで持つ。
- 台風の詳細ファイルは `specifications.json` と `forecast.json` の2本だけ。
  `detail.json` / `overview.json` / `track.json` は存在しない（404 実測済み）。
- **過去の発表を取得する手段がない。** 台風は「現在の発表」1本しか配信されず、
  過去の `issue` を遡るエンドポイントは存在しない。取り逃がした予報は永久欠損になる。
  これが15分間隔でポーリングしている理由（層2）。警報の新URL（r8）は例外的に
  直近の発表を配列で複数件返すが、保持期間は気象庁の仕様として約束されていない。
- **重複排除は台風が `issue`、警報は「`reportDatetime` + 発表内容のハッシュ」で行う。**
  `reportDatetime` 単体は一意キーにならない（2026-08-01実測: 宮古島地方で同時刻に
  別種の注意報解除が2件同時発表された）。ポーリング頻度を上げても保存量は増えない。
  増えるのは Actions の実行分数だけ。
- **アメダスの遡及可能期間は約8日**（2026-07-27 実測: 07-19 は 200、07-18 は 404）。
  `map/` も `point/` も同じ窓。日次ジョブが8日を超えて止まると層1も欠損する。
- 台風の定時発表は3時間ごと（00/03/…/21時JSTの実況を約45分後に配信）。
  日本近海に接近すると毎時発表に切り替わるが、M1実測時の台風は
  マーシャル諸島付近で遠く、**毎時サイクルは未観測**。既知の最速間隔は1時間。
