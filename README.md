# okinawa-databank

沖縄の旅行に関わる公的気象データを毎日自動記録する、時系列データの蓄積庫。

**時系列データは過去に遡って収集できない。** このリポジトリは「完璧さ」より
「回り続けること」を優先している。生データをそのまま追記し、加工も可視化もしない。

蓄積するデータには価値の層があり、それが取得頻度をそのまま決めている。

| 層 | 中身 | 取り直せるか | 頻度 |
|---|---|---|---|
| **2** | **その時点の予報**（台風の予報円・進路予想）と**警報の発表/解除の時系列** | **取り直せない。** 気象庁は「現在の発表」しか配信しない（M1実測） | **30分ごと** |
| 1 | 実績（アメダスの観測値） | 約8日間だけ遡及配信されている（M1実測） | 日次 |

層2がこのリポジトリの本体。予報は事後に残らないので、
**その時点で保存した者だけが「何日前の予報で判断できたか」に答えられる**。
層1は気象庁が配信し直しているので、頻度を上げても価値は増えない。
ただし遡及できるのは約8日なので、**8日を超えて止まると層1も永久欠損になる**。

- 出典: **気象庁**（[政府標準利用規約 第2.0版](https://www.jma.go.jp/jma/kishou/info/coment.html) 準拠）
- 収集の詳細と利用条件: [docs/sources.md](docs/sources.md)
- 背景と全体像: [HANDOFF.md](HANDOFF.md)

このリポジトリのデータを使って何かを公開するときは、必ずこの表記を添える。

> 出典: 気象庁ホームページ（https://www.jma.go.jp/）

## ディレクトリ構成

```
data/
  typhoon/YYYY/MM.jsonl        台風（発表が更新されたときだけ1行）
  warning/YYYY/MM.jsonl        気象警報・注意報（発表が更新されたときだけ1行）
  amedas/YYYY/MM.jsonl         アメダス面スナップ（1日1行・前日23:50・沖縄34地点）
  amedas_daily/YYYY/MM.jsonl   アメダス日値（1日8行・官署8地点）
state/last_seen.json           重複排除用の状態。データではない
scripts/collect.mjs            収集スクリプト（依存ゼロ・Node標準のみ）
.github/workflows/collect.yml  cron 実行
```

**追記専用。** 過去のレコードは書き換えない・消さない。訂正が必要なら新しいレコードで表現する。

## データの読み方

1行 = 1回の取得（JSON Lines）。全レコードが次の3つを必ず持つ。

| フィールド | 意味 |
|---|---|
| `fetched_at` | 取得時刻。**JST・ISO8601（`+09:00` 付き）**。実行環境が UTC でもずれない |
| `source_url` | そのレコードの取得元 URL |
| `dataset` | `typhoon` / `warning` / `amedas` / `amedas_daily` |

`error` フィールドがある行は**欠測レコード**。取得に失敗した事実そのものを記録している
（いつ・何が・なぜ失敗したか）。集計するときは除外するか、欠測として数えること。

**同じ対象のレコードが複数あることがある。** 追記専用なので、ジョブを再実行すれば
同じ `date` / `station` の行がもう1本増える（一部地点だけ失敗したときに再実行で埋められる
よう、あえて弾いていない）。読むときは `fetched_at` が最新のものを採用すること。

```bash
# 7月の欠測を数える
grep -c '"error"' data/*/2026/07.jsonl

# 那覇の日最高気温を並べる
cat data/amedas_daily/2026/*.jsonl \
  | jq -r 'select(.station=="91197" and .error==null) | [.date, .data.maxTemp[0]] | @tsv'

# 台風の中心気圧の推移
cat data/typhoon/2026/*.jsonl \
  | jq -r 'select(.error==null) | [.issue, .typhoon_number,
      (.specifications[] | select(.advancedHours==0) | .pressure)] | @tsv'
```

### typhoon

`issue`（発表時刻）が変わったときだけ1行増える。台風がなければ何も増えない。

- `specifications`: 実況と 12/24/48/72/96/120時間先予報の8パート。
  中心位置・中心気圧・最大風速・最大瞬間風速・暴風域/強風域の半径・予報円半径が**数値**で入る
- `forecast`: 同じ8パートを**図形**で持つ（予報円の接線座標、暴風警戒域の円弧）。地図描画用

### warning

沖縄の府県予報区4つを別々のレコードとして記録する。

| コード | 区域 |
|---|---|
| `471000` | 沖縄本島地方 |
| `472000` | 大東島地方 |
| `473000` | 宮古島地方 |
| `474000` | 八重山地方 |

`data.areaTypes[0]` が一次細分区域（本島中南部・本島北部・久米島など7区）、
`data.areaTypes[1]` が市町村（41）。各 `warnings[]` の `status` は
`発表` / `継続` / `解除` / `発表警報・注意報はなし`。

**警報コードの対応表は気象庁から機械可読な形で配信されていない**ため、以下は参考値。
実際の分析で使う前に、その時点の気象庁サイトの表示と突き合わせて確認すること
（`14`=雷注意報 は実測データ内の `"type":"雷危険度"` で裏が取れている）。

| 警報 | | 注意報 | |
|---|---|---|---|
| `03` 大雨 | `05` 暴風 | `10` 大雨 | `15` 強風 |
| `04` 洪水 | `07` 波浪 | `14` 雷 | `16` 波浪 |
| `08` 高潮 | | `18` 洪水 | `19` 高潮 |
| `33` 大雨特別警報 | | `20` 濃霧 | `21` 乾燥 |

### amedas

1日1行。`stations` に沖縄34地点（地点番号 91〜94 で始まるもの）が
**前日23:50時点**の値でそのまま入る。`date` がその対象日。
値は `[数値, 品質情報]` の配列で、品質情報 `0` が正常値。
`amedas_daily` の8地点より広く面をカバーするので、地域差を見るのはこちら。

> 2026-07-27 の2行だけ `date` を持たない。M2の動作確認時に毎時取得していた名残で、
> `observed_at` が示すとおり当日21:50時点の実況。追記専用なので消さずに残してある。

### amedas_daily

1日8行。官署級の8地点（那覇・名護・久米島・南大東・宮古島・与那国島・西表島・石垣島）について、
**前日23:50時点**の観測レコードをそのまま保存している。ここに入っている
`maxTemp` / `minTemp`（時刻付き）・`gust`（最大瞬間風速）・`precipitation24h` が、
実質その日の日値にあたる。`date` がその対象日。

> `precipitation24h` は「23:50 までの24時間」であって暦日の0時起算ではない。
> 気象庁が公表する正式な日降水量とは一致しないことがある。

## ローカルで動かす

Node 18 以上。依存パッケージなし。

```bash
node scripts/collect.mjs watch
```

```bash
node scripts/collect.mjs daily
```

`daily` は常に**JSTの前日**を対象にする。取得時刻ではなく日付からURLを組み立てるので、
cron が多少遅れても取る中身が変わらない。

## 自動実行と監視

GitHub Actions の cron で回している（`.github/workflows/collect.yml`）。
シークレット不要・ランニングコスト0円。

- 毎時 JST `:20` と `:50` → `watch`（台風の定時発表は :45 前後）
- JST `00:10` → `daily`（前日分）
- 消費: 約1,519分/月（private リポの無料枠 2,000分/月に対して約76%）

**枠を使い切るとその月は収集が止まる。** 残りは約480分しかないので、
手動再実行を月15回以上まわすときは残枠を確認すること
（Settings → Billing → Actions minutes）。ワークフローを増やすときも同様。

**監視は「ワークフローの失敗」そのもの。** 取得に失敗すると欠測レコードをコミットした上で
ジョブを失敗させるので、GitHub から失敗通知メールが届く。それが唯一のアラートなので、
リポジトリの通知設定は切らないこと。

なお、警報や台風に変化がない時間帯は追記が発生せず、コミットも作られない。
これは正常な状態。

### 気をつけること

- **スケジュール実行はデフォルトブランチのワークフローしか動かない。** ブランチ名を確認すること
- GitHub の cron は混雑時に数十分遅延したり、まれにスキップされたりする。
  30分間隔なのはそのため。気象庁の最速発表間隔は1時間なので、
  毎時実行だと余裕がゼロになり、1回スキップされた分の予報は永久に取れない
- 60日間まったく活動がないリポジトリはスケジュールが自動停止される。
  このリポジトリは毎日コミットが入るので通常は問題ない
